# FE-20【前端·功能】批量评估模式 · 交付说明

> 父任务：FE-20 前端 · 批量评估模式（导入 / 进度 / 结果 / 导出）（todo `rXFl8K`）
> 交付日期：2026-10-28 ｜ 工程：`frontend/`（Vue 3.5 + Vite 6 + TS strict）
> 路由：`/batch`（P8，导航第 8 项）
> 接口：`POST /api/batch/upload`、`GET /api/batch/{job_id}`、`GET /api/batch/{job_id}/export`
> 验收口径：**100 条名单可完整跑通并导出**

---

## 一、一句话结论

`/batch` 从无到有，做成一条**闭环**：名单导入 → 逐行打分 → 排序筛选 → 导出 CSV，
外加跨批次对比与 6 个任务状态的任务列表。100 行名单真跑一遍的结果是：

| 指标 | 数值 |
| --- | --- |
| 名单行数 | 100 |
| 成功出分 | **91**（成功率 91.0%） |
| 被拦下 | **9**（数据错 6 + 映射缺 3） |
| 分数均值 / 区间 | 74.11 / 64.5 – 87.0 |
| 五档分布 | 优良 22 · 较好 31 · 关注 38 · 预警 0 · 高风险 0 |
| 导出 CSV | 1 行表头 + 100 行数据，11 列，UTF-8 BOM |

本页最核心的一条判断，写在最前面：

> **这页能证明的是「一份 100 行的名单能不能一次跑完、跑不出来的那几行为什么跑不出来、结果能不能带走」；
> 不能证明的是「这 91 个分数可以直接拿去授信」。**

三条落地纪律：

- **进度不是动画**：进度条读的是接口返回的 `rows_done`，mock 模式下每轮询一次真的推进 24 行；页面没有任何 `setInterval` 自己数数。
- **失败行不藏**：默认「全部」状态，9 行被拦下的行就在表里，每行带字段名 + 原始值 + 原因，并分成「数据错」（改文件能解决）与「映射缺」（改文件没用，等 P0-1）两类。
- **导出与屏幕同源**：CSV 用页面同一份行数据、同一个 `buildExportCsv()` 生成，抽行核对分数逐位一致。

## 二、六个区块交付明细

| 区块 | 内容 | 接口 | 关键决策 |
| --- | --- | --- | --- |
| ① 名单导入 | 拖拽 / 选择文件、内置演示名单（100 行）、**六条文件级校验**逐条给结论、前 8 行预览 + 字段级问题标注 | `POST /api/batch/upload` | 证书编号不合法**不算**文件级失败 —— 否则 100 行里 1 行坏号会把整份退回去 |
| ② 任务进度 | 进度条（`rows_done / rows_total`）、状态徽标（4 值）、5 个 KPI、五档分布、失败原因分组（可点行号回表） | `GET /api/batch/{job_id}` 轮询 | 处理中明确标「非终局」；成功率**分母是名单总行数**，不是已处理行数 |
| ③ 评估结果 | 企业标识 / 信用分 / 风险分级 / PD / 主要贡献因子 / 是否异常 / 评估状态；排序（5 列）、按档多选筛选、搜索、只看异常、分页 25 行、行展开追溯 | 同 ② | 未出分的行**永远沉底**（不参与排序）；主要贡献因子只显 `x125` |
| ④ 导出 | 11 列清单（Q3 模板 6 列 + 评估结果 5 列）、失败行处理说明、文件名预览、下载 CSV、示例导出 | `GET /api/batch/{job_id}/export` | 未完成的任务**不出现导出按钮** —— 导出跑一半的 CSV 比不给更糟 |
| ⑤ 跨批次对比 | 选历史批次 → `as_of` 不同先拦一次 → 点「我已知晓」才给逐行差异（默认只看档位跳变） | 复用 ② 的任务快照 | 差 12.46 分说成「模型版本效应」，不说成「企业经营改善」 |
| ⑥ 任务列表 | 6 个任务覆盖 排队 / 处理中 / 完成 / 历史批次 / 空名单 / 解析失败，点一行切换 | 同 ② | 空名单写「0 行（文件只有表头）」，不写「0 家已评估」 |

## 三、契约与数据

### 3.1 四份契约 + 两份 CSV（`scripts/build_batch_contracts.py`，零第三方依赖、seed 固定、字节级可复现）

| 文件 | 大小 | 内容 |
| --- | --- | --- |
| `batch_submit.json` | 1.5 KB | 受理回执的形状（`job_id` / `rows_total` / `rows_accepted` / `estimated_seconds` / `field_validate`） |
| `batch_status.json` | 311.7 KB | 6 个任务快照 + `export_columns` + `field_validate` + 7 条读图问答 |
| `batch_evidence.json` | 113.2 KB | 逐行追溯：名单行 → `userid` → 分数 → 归因 → 导出列 |
| `batch_notes.json` | 2.5 KB | 「这一页能证明什么、不能证明什么」7 条（接口挂了也能显示） |
| `public/fixtures/batch_demo_100.csv` | 8.5 KB | 100 行演示名单（6 行字段错 + 3 行映射缺），BOM + CRLF |
| `public/fixtures/batch_export_100.csv` | — | 示例导出，表头与 `buildExportCsv()` 逐字一致 |

### 3.2 生成器的硬约束（不满足直接 `SystemExit`）

1. **分数直取 P7**：91 个成功行的 `credit_score` 与 `enterprise_detail.json` 同 `userid` 差 > 1e-9 即拒写盘；
2. **档位由同一切点派生**：`risk_band` 必须等于 `band_of(score, [50,60,70,80])` 的结果；
3. **失败行没有分数**：`credit_score / pd / risk_band` 全为 `null`，且必带 `error.field + code + message`；
4. **证书编号名单内唯一**；
5. **名单与契约自洽**（本轮新增）：声明是哪一类错误，就核对该字段的值**真的违反了那条规则**。

> 第 5 条是这次真抓到 bug 才补的：`FIELD_ERRORS[7]` 写的是「证书编号只有 10 位」，但构造分支
> `f"GR{year}{serial:06d}"` 对 8 位序列号**不会截短**，写进 CSV 的其实是合法编号 ——
> 契约里第 7 行被判失败，前端拿同一份 CSV 重跑时它却通过了。同一行两套结论，是最难查的一类问题。
> 现在：① 断言直接拦下（`行 7：声明为 CERT_FORMAT，但 证书编号='GR202533000959' 并没有违反该规则`）；
> ② 构造改成显式切掉末两位；③ 分流的判断依据从「说明文案里有没有『空格』」改成行号（按文案分流，改文案就静默走错支）；
> ④ 冒烟里真的把演示 CSV 灌进本地队列跑一遍，与契约快照逐行比对 `userid / 分数 / 档位 / 状态`。

### 3.3 名单规模的设计取舍

真实名单 500 家，可映射面板只有 12 个 `userid`。一企一行只能跑通 12 行，那种"验收"证明不了 100 行规模下可用；
同一企业重复出分又等于把批次噪声当企业差异。折中方案是**名单快照**：面板企业循环占用，每次占用记成一条独立的名单档案件（证书编号不同），
分数直取该企业档位路径内的契约值。这样 100 行规模、按档筛选、分页、导出 100 行、进度轮询都在真实体量下验到了。

## 四、红线落地

| 红线 | 本页怎么落 | 刻意不做的 |
| --- | --- | --- |
| ① 不混排来源 | 导入区带 `SectionBadge`（`dataset=real_panel` / `source=contract_spec`）；本页只有这一个来源 | 不在批量页混入合成图指标 |
| ② 语义未知只显代号 | 主要贡献因子 100% 是 `xNNN`；页面写明「P0-2 字段字典未到位」 | 不写「研发投入强度」这类编出来的名字 |
| ③ 不混 AUC 噪声地板 | 结果表上方一条警示带写明「AUC ≈ 0.59 vs 噪声地板 0.477，仅高出 0.1」；本页不出 AUC 图 | 不在分数列旁边画 0.477 基准线 |
| ③' 批量结果不是授信依据 | `p8-caveat` 常驻结果表上方；读图问答第 4 条专门回答「这些分数能拿去授信吗」 | 不用「评级」「授信建议」这类词 |
| ④ 跨快照不可比 | `diffJobs()` 第一返回是 `comparable`；`as_of` 不同先拦一次，用户点确认才给逐行差异 | 不把两个批次并排画趋势线 |

## 五、接口层与降级

### 5.1 三个端点为什么走独立实现

P1–P7 的端点都只读静态契约，走 `call()` 一条通道；批量三端点是**有状态**的（提交 → 轮询 → 导出），
所以 `api/index.ts` 里单独实现：

- **real**：`POST /batch/upload` 传 multipart，`GET /batch/{job_id}` 与 `/export` 直接透传，失败如实抛出；
- **auto**：真实接口不可用时降级到本地队列；
- **mock**：`api/mock/batch.ts` 的内存任务队列（每次轮询推进 24 行，与真实后端同一套校验规则）。

### 5.2 降级

`fetchBatchStatus()` 在 real 模式下对响应多要一条：`data.jobs` 必须是数组。
不满足就如实抛错 → 页面出「批量任务列表未能加载 + 原因 + 下一步 + 重试」，
**不悄悄换成 mock 列表**（那会让人以为后端已经有 6 个任务了）。

读图问答被移到 `v-else` **之外**：接口挂了，口径说明更该留着。接口不可用时退回 `batch_notes.json`（与 `batch_status.json` 的 notes 同源）。

### 5.3 三个会咬人的实现细节

| 坑 | 表现 | 现在怎么做 |
| --- | --- | --- |
| `shallowRef` + 原地修改 | mock 的 `advance()` 原地推进同一对象，`computed` 认为引用没变不重算 → 接口在推进、页面停在「已处理 0 / 100 行」 | 在 mock 边界返回 `structuredClone(job)`，每次轮询都是新对象 |
| `RouterView :key="route.fullPath"` | 轮询里 `router.replace({ query: { job } })` 每换一次 URL 就整页重建 → 提交完名单页面闪回空导入区，回执不出现 | key 改用 `route.path`：换页才重建，query 变化交给页面自己响应 |
| 失败行重复累加 | `advance()` 每批都把 `state.failed` 并进 evidence → 「已处理 115 / 100 行」 | `[...evidence.filter(ok), ...slice, ...state.failed]`，失败行只来自固定集合 |
| 两条色带同 testid | 进度区的只读分布 + 结果表的可点筛选都叫 `risk-band-bar`，冒烟点到 disabled 的那个 | `BandBar` 加 `k` prop → `risk-band-bar-progress` / `-filter` |
| 窄屏横向溢出 | 五段等分色带 + 三张表把整页顶出 226px | 色带允许换行（`flex: 1 1 40px`）；导入预览表 / 对比表补 `overflow-x: auto` 容器 |
