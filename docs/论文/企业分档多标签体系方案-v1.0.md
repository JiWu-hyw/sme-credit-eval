## 0. 一句话结论

**有方案，而且数据库早就把多标签架构预留好了；眼下的瓶颈是采集，不是建模。**

库里 `ads_label` 允许 4 类标签任务，`dim_qual_type` 定义了 4 级资质阶梯，但实际只填了 1 类任务、2 类资质，且 `qual_rank` / `max_qual_rank` 是常数 3。真正能界定「企业变差」的结果型标签样本只有个位数。

因此分两步走：**现在就用现有字段做一版可审计、可复现的五档规则基线（L0）**，再用按性价比排好序的采集清单把它升级成多标签潜变量模型（L1/L2）。L0 定位是对照基线，**不是**「企业信用好坏」的最终结论。

---

## 1. 先把三个词分开

| 词 | 含义 | 在库里的位置 |
|---|---|---|
| 企业好坏 | **潜变量**，不可直接观测。它是「未来会不会出事、能不能持续变好」的潜在状态 | 无 |
| 标签 | 潜变量的**可观测锚点**（监督信号 y），每个锚点只覆盖一个侧面、都带噪声 | `ads_label`、`ads_survival_period`、`dim_enterprise` 各类标志位 |
| 档次 | 模型或规则给出的**有序输出**（A/B/C/D/E），是对潜变量的估计 | 目前无，本方案定义 |

多标签的作用不是「把几个 0/1 加权求和」，而是给同一个潜变量提供**多个相互独立的锚点**，用来交叉校准和验证。判断是不是真多源，只看一条：

> **独立性判据**：如果两个标签都由同一批公示名单差分产生（例如「资质断档」与「资质晋级次数」），它们是同一个信号重复计权，不构成多源印证。

这条判据直接否掉了「多采几份高企名单就能做多标签」的想法。

## 3. 四轴标签体系

| 轴 | 观测什么 | 现有字段 | 可得档次 | 与其他轴的独立性 | 当前缺口 |
|---|---|---|---|---|---|
| **A · 结果型（硬）** | 违约 / 严重失信 / 经营异常 / 注销 / 复核未通过 | `serious_dishonesty_cnt`、`biz_anomaly_cnt`、`biz_status`、`risk_negative_cnt` | 二分类，用作**一票否决** | 最强，唯一能真正界定「坏」 | 样本 2 / 1 / 3 家；无撤销公告 |
| **B · 资质阶梯（序）** | 科技型中小 → 高企 → 专精特新 → 小巨人 | `is_*` 标志位、`dim_qual_type`、`max_qual_rank` | 4 级有序 | 与 A 部分独立 | 无时间戳；`max_qual_rank` 恒 3 |
| **C · 时间动态（生存）** | 存续 / 断档 / 晋级速率 | `ads_survival_period`、`ads_label` | 多期风险层 | ⚠️ **与 B 同源于公示名单，不独立** | 21 事件，口径仍是「没再申报」 |
| **D · 外部连续分箱** | 第三方信用 / 技术等级 | `qcc_credit_level_ord`、`qcc_tech_level_ord`、`qcc_score` | 5 / 12 级 | 与 A–C 独立 | 循环定义风险；`ods_qcc_*` 公开分发需确认服务条款 |

四轴里只有 **A 是结果**，B/C/D 都是状态或过程量。任何把 B/C/D 直接称为「企业好坏」的写法都是过度解释。

## 4. L0：五档规则基线（现有数据，可立即复现）

### 4.1 为什么用字典序分层，而不是加权打分

加权求和需要主观权重，且用第三方等级定档、再用同一批等级验证会形成循环论证。L0 改用**硬约束 → 有序主序 → 兜底**的字典序规则，每条判据可审计、无权重、可单测。

### 4.2 判据（v1.7 已落成 `v_enterprise_grade_l0` 视图）

```sql
WITH b AS (
  SELECT d.enterprise_id,
         COALESCE(d.serious_dishonesty_cnt,0) AS sd,
         COALESCE(d.biz_anomaly_cnt,0)       AS ba,
         d.biz_status,
         COALESCE(d.risk_negative_cnt,0)     AS rn,
         COALESCE(d.is_little_giant,0)       AS lg,
         COALESCE(d.qcc_tech_level_ord,0)    AS tech,
         COALESCE(d.qcc_credit_level_ord,0)  AS cred,
         COALESCE(l.label_value,-1)          AS lab
  FROM dim_enterprise d
  LEFT JOIN ads_label l
    ON l.enterprise_id = d.enterprise_id
   AND l.label_task = 'qual_survival'
)
SELECT CASE
  WHEN sd > 0 OR ba > 0
    OR (biz_status IS NOT NULL AND biz_status <> '开业') THEN 'E 预警'
  WHEN rn > 0 OR lab = 1                                THEN 'D 观察'
  WHEN lg = 1 OR tech >= 5                              THEN 'A 引领'
  WHEN tech = 4 AND cred >= 11                          THEN 'B 优质'
  ELSE 'C 稳健'
END AS grade, COUNT(*) AS n
FROM b GROUP BY grade ORDER BY grade;
```

### 4.3 实测家数（500 家全覆盖）

| 档 | 判据 | 家数 | 语义边界 |
|---|---|---:|---|
| **A 引领** | 小巨人 或 技术等级卓越 | **44** | 资质/技术领先，**不等于信用免检** |
| **B 优质** | 技术等级优秀 且 信用等级 ≥ 11 | **95** | 同上，仍是状态描述 |
| **C 稳健** | 其余 | **275** | 主体层，内部差异最大，后续优先细分 |
| **D 观察** | 风险负面=1 或 资质断档信号 | **83** | 候选 85 = 风险负面 67 + 资质断档 21 − 交叉 3；其中 2 家因同时命中 E 档硬约束被优先归入 E，故实得 83 |
| **E 预警** | 严重失信 / 经营异常 / 非开业 | **3** | 样本量不足以做任何性能评估 |

五档家数闭合：44 + 95 + 275 + 83 + 3 = 500。`admin_penalty_cnt` 明确排除在判据之外（见 §2）。`lab = -1` 表示未打标的 193 家，不参与 D 档判定——它们不是负例；67 家风险负面中有 27 家属于此类，其余 40 家为已打标企业。

### 4.4 L0 的定位

- ✅ 可以：作为可解释基线、与后续模型对照、检查「档次 → 事件率」是否单调、写进论文方法章的规则对照节
- ❌ 不可以：当作「企业信用好坏」结论、对外发布、上生产、报准确率
- 已知循环定义：A/B 档的判据用了 `qcc_tech_level_ord` / `qcc_credit_level_ord`，因此**不能用这两个字段去验证 L0 分档是否正确**

## 5. 五个必须写进论文局限的陷阱

1. **循环定义**：用第三方等级分档，再用第三方等级验证。规避：外部效度只用 A 轴结果型标签。
2. **伪多源**：`qual_survival` 与资质晋级同源于公示名单，两者高度相关；实测 21 正例 100% 为 `n_events=1`、286 负例 100% 为 `n_events≥2`，标签与名单记录数完全共线。
3. **样本塌陷**：E 档 3 家、D 档中资质断档 21 家、验证集正例 2 个。任何分档性能的点估计都无意义，必须给每档家数与置信区间。
4. **语义污染**：名单是「当年新认定名单（增量）」，不是存量有效名单，跨年留存仅 0.1%–0.3%，「未出现」≠「资格没了」；「未再申报」≠「经营变差」。
5. **后视泄漏与口径混用**：分档必须只用 `v_model_dataset_asof_flat` 且固定一种 `as_of_policy`；全量快照 `ads_model_dataset` 含标签窗口内信息，只能作泄漏基线。此外 A/B 两套数据仍混在同一 API，`score.value` 恒 null 是设计。
6. **合规**：`ods_qcc_*` 系列公开分发前须确认服务条款；分档结果若对外发布同样受此约束。

## 6. 升级路线（按性价比排序，不按采集量排序）

| 优先级 | 动作 | 补哪个轴 | 成本 | 收益 |
|---|---|---|---|---|
| **P0 ✅ 已落地（v1.7，2026-11-07）** | 把 L0 落成 `v_enterprise_grade_l0` 视图 + 守卫单测；在 `configs/field_gap_registry.json` 显式登记另外 3 个 `label_task` 为「源未接入」；统一 as-of 口径 | 全部 | 零采集 | 分档可复现、口径可审计；清单见 §9 |
| **P1（最推荐先做）** | ① 高企「撤销 / 复核未通过」公告；② 经营异常 / 严重失信名录；③ L1 科技型中小、L3 专精特新、小巨人名单**带年份与批次** | A + B | 公开网页/PDF 采集 | 直接补齐唯一能界定「坏」的结果标签 + 补齐 4 级阶梯时间戳，性价比最高 |
| **P2** | MSME 信贷违约（1,707 家，Kaggle）、SBA Loans（90 万条，MIS_Status） | 外部效度 | 一次下载 | 注意：**不是**把外部标签贴到浙江企业上，而是验证「特征 → 档次」映射能否跨源迁移 |
| **P3** | 财报时序、工商状态时序、司法文书 | A + 连续层 | 高 / 部分无免费源 | 经营好坏的直接证据，可选项 |

**为什么不先扩样本**：把名单前推 2019/2020 或扩到 3,000–5,000 家，只增加同一类共线标签的数量，不增加标签的**维度**；在 A 轴仍是 2–3 家真事件时，扩样本不会让「好坏」更可辨识。

## 7. L1/L2 建模方法

**不要加权求和。** 推荐与 L0 同构的三层结构：

```
硬约束层（A 轴：结果型真标签）  → 一票定 E 档，不参与打分
        ↓
有序主序（B 资质阶梯 + C 多期生存）→ ordinal / cumulative-link 回归
        ↓ 或 多任务学习：各轴独立 head、共享表示
同档内排序（D 轴连续分位数）      → 只在 C 档内部细分，不跨档
```

**验证三件套（缺一不可）**

| 检验 | 做法 | 通过标准 |
|---|---|---|
| 外部效度 | 用 A 轴真标签算各档事件率 / AUC | 事件率随 A→E 单调递增，且置信区间不重叠 |
| 内部一致性 | bootstrap 重采样看档次稳定性 | 跨重采样档位漂移率有界 |
| 跨口径稳定性 | 分队列（2021/2022）、分 `as_of_policy` 各跑一遍 | 结论方向一致；不一致必须报告而非择优挑一个 |

**报告红线**：分档不报「准确率」；每档必须带家数与置信区间；21 正例、验证集 2 个正例的限制必须写明；升版后旧实验结论不得跨版本比较。
