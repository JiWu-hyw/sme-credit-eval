## 一、问题 1 ｜`companies` 补企业身份字段 —— **采纳全部 4 处修订**

前端 4 处修订逐条后端确认：

| # | 前端建议 | 后端裁决 | 落地 |
|---|---|---|---|
| ① | `name: string \| null`，键恒存在；`id` 仍是业务主键 | **同意**。企业名可重名/可工商改名，`name` 不得作索引键；`explanations[name]` 串行/覆盖风险成立 | `companies[].name` 恒出现，缺映射时 `null` |
| ② | `credit_code: string \| null`，全局唯一；冲突置 `null` + `mapping_conflict: true` | **同意**。信用代码是唯一可核验身份，冲突显式暴露优于静默取一 | 增 `credit_code` + `mapping_conflict` |
| ③ | `label: any \| null`、`correct: boolean \| null`；`correct` 为评测态字段 | **同意**。真实面板上线后 `label`/`correct` 应消失，前端不得因缺字段崩 | 增字段可空语义 |
| ④ | 排行榜按地市筛选 → 一并下发 `region_code`/`region_name` | **同意**。`dim_enterprise` 已有地区字段，一次下发省逐企业二次请求 | 增 `region_code`/`region_name`（可空） |

**后端补充（demo 降级口径）**：真实面板映射键（P0-1）到位前，`export_dashboard.py` 的 demo 版 `name`/`credit_code`/`region_code`/`region_name` 一律返回 `null`、`mapping_conflict` 返回 `false`；前端按回执 §1.2 降级文案 `name ?? \`企业#${id.slice(-6)}\`` 处理，无需后端干预。

## 二、问题 2 ｜实体枚举中文 —— **采纳 B+，`enums.yaml` 后端持有**

- 采纳回执 §2.3 四步：`configs/enums.yaml` 唯一权威源（后端维护、进 Git）→ 构建期派生 `configs/enums.json` → 接口 payload 同时下发 `type`（英文，逻辑用）+ `type_cn`（中文，展示用）→ `meta.enums_version` 供前端启动断言。
- **`theme_var` 与 `viz_theme.yaml` §entity_category 同源**：类型→颜色映射收归权威源，前端不再自定色，与既有裁决口径一致。

- 前端 `entity.ts`（`entityLabel`/`entityColor`）消费 `enums.json`，删除 `renderGraph`/`showDetail` 两处硬编码——该动作归前端 FE，不属后端。

**后端落地（本裁决执行）**：新建 `configs/enums.yaml` + `scripts/build_enums.py`（yaml→json 派生，仿 `build_viz_theme.py` 同构，带 `--check`）。

## 三、问题 3 ｜局部解释补 `feature_shap` —— **采纳对象式 + 全字段**

- 结构照回执 §3.2，`explanations[id]` 增 `feature_shap` **对象**（非裸数组）：

```json
"feature_shap": {
  "method": "tree_shap",
  "score_direction": "pd",
  "base_value": 0.107,
  "prediction": 0.183,
  "top_k": 5,
  "coverage": 0.72,
  "items": [
    { "f": "x37", "name": null, "semantic_known": false, "label_ref": "字段字典待补",
      "value": 0.0836, "raw_value": 1.42, "median": 0.81 }
  ]
}
```

- **`name` 一律先置 `null`**：为 `semantic_known:false` 的未知字段编业务名违反红线二（后端原样透传 `semantic_known`/`label_ref`，前端绝不为 `semantic_known:false` 渲染业务名）。
- `score_direction` 定为 `"pd"`（正值 = 推高 PD/风险）；前端据此定红绿方向，避免国内「涨红跌绿」语境下风险信号反色。
- `status`（`ready`/`pending`）区分「未计算」与「算出但为空」，两种语义不得混。

**后端落地依赖**：`feature_shap` 由 `src/app/local_explain.py` 产出；真实 SHAP 计算依赖 `src/explain/` 特征级归因，未就绪前 `feature_shap.status="pending"`（或字段缺省），前端占位「局部解释生成中」，不再用全局 `importance` 顶替。

## 四、问题 4–6 ｜前端新增诉求 —— 后端逐条裁决

### 问题 4｜`id` 统一 string 且稳定 —— **同意**

- 现状实测：`companies[].id` 为**数字**（0–79），而 `explanations` 键为 `str(c)`（"0"…"79"）——两侧类型已不一致，正是前端指出的「JS 对象键是字符串、number 会静默取不到值」的坑。
- **裁决**：`id` 统一 `string`。真实面板用 `enterprise_id`（`ENT`+12hex，大写，`dim_enterprise` 既有稳定键）；demo 版用 `company_{i}`（与 `graph.nodes[].id` 对齐），`explanations` 键、`graph` 节点 id 随之统一。
- 排序/分页只改数组顺序，不改 `id` 语义。

### 问题 5｜`meta` 增版本锚点 —— **同意**

- 统一响应包 `meta` 增 `contract_ver` / `enums_version` / `schema_version`。
- 本次取值（MAJOR 升版）：`contract_ver: "v2.0"`、`enums_version: "v1.0"`、`schema_version: "v1.0"`。
- 前端启动断言三者，不匹配显示「契约版本不一致，请刷新」，而非静默错渲。

### 问题 6｜数值精度与 null 语义 —— **同意**

- `score`：整数 **0–100**（现状 `round(100−pd·100, 2)` 带 2 位小数，改为 `round` 取整）。
- `pd`：后端下发**未四舍五入的原始 float**（现状 `round(pd, 4)` 改为原值），展示格式由前端定。
- 缺失一律 `null`，不用 `-1`/`0`/`""` 哨兵——与《后端完整答复》§5.2「数据库层一律 NULL，不用哨兵」一致。
