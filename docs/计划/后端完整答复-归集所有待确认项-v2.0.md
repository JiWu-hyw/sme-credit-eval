# 第一章　数据契约类（接口契约 Q3 / Q5）

## Q3 ｜ 批量导入的名单模板列名规范

**答复：无需再"约定"——后端侧契约已冻结并实测跑通。直接采用下表，前端照此出模板与预校验即可。**

### 3.1 文件级规范
- **格式**：CSV，编码 **UTF-8 with BOM（`utf-8-sig`）**；分隔符 `,`；LF / CRLF 均可；无合并单元格、无多级表头。
- **结构**：**单表头行 + 每条企业一行**；禁止分组小标题、空行、页脚合计行。
- 若必须走 Excel：`.xlsx` **首个工作表**，A1 起始，列名与列序同下表。
- 字段内含逗号/引号时，整字段加双引号（标准 CSV 转义）。

### 3.2 列名规范（冻结 v1.0，共 6 列，顺序不可调整）

| 列序 | 列名 | 类型 | 必填 | 约束 / 说明 |
|---|---|---|---|---|
| 1 | `序号` | 整数 | 是 | 文件内顺序号。**仅作留痕，不参与主键、不去重**；落 `ods_qual_company_raw.seq_no`（非数字时置 NULL，不拒行）；多批次合并时会重号，由后端按证书编号重排 |
| 2 | `企业名称` | 文本 | 是 | 公示原文名称。**前端原样透传，勿做任何清洗**（`name_norm` 由后端派生） |
| 3 | `证书编号` | 文本 | 是 | 正则 `^GR\d{12}$`（GR + 12 位，例 `GR202133000001`）；同文件内不得重复 |
| 4 | `来源年份` | 整数 | 是 | 认定年度，如 `2021` / `2024` |
| 5 | `批次` | 文本 | 否 | 原文留痕列，**不驱动库表** `batch_no`；库表 `ods_qual_notice.batch_no` 由后端按公告固定为 `2021-1` / `2021-supp` / `2024`；本列缺失即用公告默认值 |
| 6 | `发证日期` | 文本 | 否 | `YYYY-MM-DD`；原文为非标准格式时后端保留原文并留痕 |

一行一企业。**缺列直接拒收**（后端按必需列名集合精确校验，不做模糊别名兜底）。

### 3.3 与库表的映射（后端职责，前端无需感知）

| 模板列 | 落库位置 |
|---|---|
| `企业名称` | `ods_qual_company_raw.company_name` |
| `序号` | `ods_qual_company_raw.seq_no`（留痕；非数字置 NULL） |
| `证书编号` / `来源年份` / `批次` / `发证日期` | `ods_qual_company_raw.raw_payload`（JSON 原文保全） |
| ——（后端按公告定义，**模板列不驱动**） | `ods_qual_notice.batch_no` / `fact_qualification.batch_no` = `2021-1` / `2021-supp` / `2024` |
| `来源年份` | `fact_qualification.year` |
| ——（后端派生，模板不提供） | `dim_enterprise.enterprise_id` = `'ENT' + md5(name_norm)[:12]`（大写）、`name_norm` |

> 设计要点：**模板列名用中文（面向中文公文来源），库表字段用英文 `snake_case`**，两者的映射完全在 `collect_pool.py` 内完成。前端不做列名的业务判断，因此库表字段改名不会波及前端模板——这是刻意的解耦。

### 3.4 固化与变更
- 模板版本号 **`import_template v1.0`**，与 schema v1.0 同期冻结。
- 变更流程：**先改后端契约（`schema.sql` + `manifest`）→ 升版本 → 通知前端**；后端不提供旧列名的兼容兜底。
- 可运行样例与校验工具：`scripts/pdf_to_csv.py`（官方 PDF → 标准 CSV）、`scripts/collect_pool.py --dry-run`（模板校验，不写库）。
- 导入接口：`POST /api/data/import`。前端只做**文件级**预校验（类型 / 大小 / 必需列名存在）；**字段级校验以后端返回为准**。

## Q5 ｜ 字段命名冲突时的仲裁依据

**答复：同意"以数据契约为唯一仲裁依据"这一原则，并把"数据契约"落到可执行的契约边界上，避免两份文档互相引用造成悬空。**

### 5.1 「数据契约」的确切指代（优先级自上而下）
1. `src/data/schema.sql` —— **可执行 DDL，机器校验为准**
2. 《标准数据库 · 数据字典与设计说明 v1.0》§6 命名与口径约定 + `configs/db_schema_manifest.json`
3. 《后端 API 与数据表 Schema（初稿 v0.1）》—— API 层补充；与前两者冲突时，**以前两者为准**

即：**以已冻结、可校验的 schema 为准，而非以某份文档的表述为准。** 《API 与数据表 Schema》目前仍是 v0.1 初稿，发生冲突时应优先修订它，而非改动 schema。

### 5.2 命名规范（前端对齐用，团队必须遵守）
- **表 / 字段**：全小写英文 `snake_case`；表前缀分层 `meta_ / ods_ / dim_ / fact_ / dws_ / ads_ / ext_`；桥表 `bridge_*`；视图 `v_*`
- **键**：主键与外键统一 `*_id`；代理键——企业 `ENT`+12hex（大写）、发明人 `INV`+10hex、专利 = 公开号；**禁止用名称做外键**
- **时间**：日期 `TEXT 'YYYY-MM-DD'`、年月 `TEXT 'YYYY-MM'`、年份 `INTEGER`、时间戳 `*_at`
- **量纲**：布尔 `is_*`（0/1）、计数 `n_*`、率 `*_rate`、比 `*_ratio`
- **枚举**：一律由 CHECK 约束固化（`status` / `patent_type` / `split` 等），**前端不得自定义枚举文本**
- **缺失**：数据库层一律 NULL，**不用 -1 / -999 哨兵**；替代口径字段必须伴随 `*_flag` 标注

### 5.3 接口层与库表的命名映射（避免二次映射）
- API JSON 字段**直接沿用库表字段名**（`snake_case`），不转 camelCase；URL 路径用 `kebab-case`
- 日期字符串格式与库表一致（`YYYY-MM-DD`）
- 既有前端产物 `web/dashboard_data.json`（`meta / companies / importance / graph / explanations`）**保持不变**；`/api/company/{id}/graph`、`/api/company/{id}/explanation` 直接返回其子结构，**前端无需改版**

### 5.4 冲突裁决流程（三步，含时限）
1. **发现冲突方**记录到文档变更记录或 issue，**不得自行改名、不得两套名并行**；
2. **后端 24h 内裁决**：默认以 schema 为准；确需变更则走 DDL 变更 → 升 schema version → 更新 `manifest` → 登记数据字典；
3. **变更同步**至 §6 命名约定 + 受影响 API，并通知前端。**未经裁决的字段名不得进入前端代码。**

### 5.5 版本锚点
schema **v1.0**（2026-10-14 冻结）；`configs/db_schema_manifest.json` 作为字段清单的机器可比对基线。

## 第 2 条 ｜ `outputs/` 统一管理 —— **统一管理，由数据管道侧收口**

### 现状（实测，确实是"各脚本各自写"）
`outputs/` 目前有 5 个产物，由至少 3 处不同脚本写、且路径硬编码：

| 产物 | 写入方 | 消费方 |
|---|---|---|
| `shap_global.json` / `shap_global_summary.png` / `shap_top_features.csv` | `src/explain/global_shap.py` | 前端（契约）+ 报告 |
| `baseline_results.json` | 基线实验脚本 | 报告 |
| `gat_panel_results.json` / `gat_panel.pt` | 面板图/GAT 脚本 | 报告 + 模型侧 |
| `outputs/demo/*` | `run_demo.py` | 演示 |

**风险**：① 同名产物互相覆盖、无版本痕迹；② 前端"读哪个文件"靠口头约定；③ 中间产物与对外契约产物混放，引用时无法判断权威版；④ 无产物索引，找不到"这份 JSON 是谁在哪次运行生成的"。

### 决策（我方拍板，需前端确认消费方式）
**统一管理，但不动数据内容**，只统一"出口位置 + 命名 + 索引"：
1. **唯一路径字典**：新增 `configs/paths.yaml`，键=产物名、值=相对路径；脚本**只允许** `out_path("shap_global")` 取路径，禁止硬编码 `"outputs/..."`。
2. **目录分层**（都在 `outputs/` 下，不改现有前端读取路径）：
   - `outputs/contracts/` — 对外契约产物（前端/报告消费），只增不改；
   - `outputs/reports/` — 报告用图表；
   - `outputs/work/` — 中间过程产物，可随时删除、不进库、不引用；
   - `outputs/manifest.json` — 产物索引。
3. **命名规范**：`<域>_<内容>_v<契约版本>.<ext>`，如 `shap_global_v1.json`。**文件名带版本，禁止就地覆盖**。
4. **`outputs/manifest.json` 每条记录**：产物名 / 路径 / 生成脚本 / 生成时间 / 行数或大小 / `sha256` / 契约版本 / 状态（`contract` 或 `experimental`）。**前端只读 `status=contract` 的产物**。
5. **破坏性变更**：升到 `contracts/v2/`，前端按 manifest 的 `contract_ver` 适配，旧版保留至少一个里程碑周期。

### 落地（我方执行，不含前端改动）
`configs/paths.yaml` → `src/common/paths.py`（`out_path()` / `register_artifact()`）→ `scripts/build_outputs_manifest.py`（生成 manifest）→ 改写现有 4 个写入点（`global_shap.py`、基线、面板图、`run_demo.py`）。

**需前端确认的唯一一点**：是否接受"增加一次读 `outputs/manifest.json`"作为唯一入口（现有 `dashboard_data.json` 结构与路径**保持不变**）。

## 第 3 条 ｜ 五档风险分级语义标签 —— **标签现在就能固化；阈值现在不能固化为"绝对 PD"**

### 3.1 语义标签：建议与监管五级分类一一对照

| 本项目档位 | 语义标签 | 对应《商业银行金融资产风险分类办法》五级分类 | 监管锚点（该办法第 10–13 条） |
|---|---|---|---|
| 1 | **优良** | 正常类 | — |
| 2 | **较好** | 关注类 | 本金/利息逾期即至少关注（操作性/技术性 7 天内短期逾期除外） |
| 3 | **关注** | 次级类 | 逾期 **> 90 天**、或已发生信用减值 |
| 4 | **预警** | 可疑类 | 逾期 **> 270 天** |
| 5 | **高风险** | 损失类 | 逾期 **> 360 天**、或已进入破产清算 |

> **可直接采纳的强制规则**：若将来接入逾期数据，**逾期天数锚点优先级高于模型分**——落在锚点区间的企业直接强制归入对应档位，模型分不得上调。

### 3.2 为什么现在不能固化绝对阈值（关键结论）
现有模型在真实面板上的区分度**仅略高于噪声地板**：行级 AUC 0.596、企业级 0.473、置换对照 0.492，GAT 0.572。这意味着：
- 模型输出的 PD **未经校准**，不是真实违约概率；
- 现在若按"PD ≥ 某绝对数→高风险"划档，会出现**档位分布完全由未校准分数量纲决定**的伪精度问题；
- 但**五档的语义标签可以先固化**（它是业务语言，不依赖模型校准）。

### 3.3 建议两版阈值（先分位、后绝对）
**v1.0（现在启用，分位法定档）**：

| 档位 | 语义标签 | 分数分位（降序） | 目标占比 |
|---|---|---|---|
| 1 | 优良 | 前 15% | 15% |
| 2 | 较好 | 15%–40% | 25% |
| 3 | 关注 | 40%–70% | 30% |
| 4 | 预警 | 70%–90% | 20% |
| 5 | 高风险 | 后 10% | 10% |

> **后档取 10% 的依据**：留出集实测正例率 **10.7%**（75/698），"高风险档占约 10%" 与样本真实正例率同量级，业务侧有直觉锚点。

**v2.0（模型校准后启用，绝对阈值；现不启用）**：

| 档位 | 语义标签 | PD 区间 |
|---|---|---|
| 1 | 优良 | < 1% |
| 2 | 较好 | 1%–3% |
| 3 | 关注 | 3%–6% |
| 4 | 预警 | 6%–10% |
| 5 | 高风险 | ≥ 10% |

> ⚠️ **需业务侧注意**：现行约定 `credit_score = 100 − 100·PD` 是**线性**映射，配 v2.0 阈值会让"优良档"要求分数 ≥ 99，高档区间被压得极窄。可选：① 保留线性分数、仅档位用分位法（即 v1.0）；② 改非线性映射（如 `100·(1−PD)^k` 或分位映射）。**这是第 3 条最需业务侧拍板处。**

### 3.4 契约与校验（后端负责实现，均外置可配）
- **字段建议**：`risk_band`（1–5 整数）+ `risk_label`（中文语义）+ `risk_band_ver`（如 `v1.0`）+ `band_rule`（`quantile` / `calibrated_pd` / `overdue_override`）。阈值写在 `configs/risk_bands_v1.0.yaml`，**不硬编码**。
- **颜色约定**（符合国内风险语境）：高风险=红、预警=橙、关注=黄、较好=浅绿、优良=绿。
- **每次生成必须落校验并写入 manifest**：① PD 均值随档位单调递增；② 每档样本数 `n_per_band` 不为 0；③ 阈值版本号随产物一起落盘。

### 统一响应包（后端定义）
```json
{ "code": 0, "message": "ok", "data": { ... }, "meta": { ... } }
```
- `code`：**0 成功**；非 0 业务/阻塞（如 `"CONTRACT_PENDING"`、`"LABEL_PENDING"`、`"BATCH_RUNNING"`）。
- **HTTP 状态码与业务码分离**：HTTP `200` 仅表示"请求已被受理"，**成功判定一律看 `code === 0`**；批量导入的"部分行失败"仍为 `code=0`（数据级错误不改变业务码，看 `data.summary.failed`）。同层错误码补充：`IMPORT_REJECTED`（文件级拒收，如缺列/编码错）。
- ⚠️ **勘误（v1.1）**：《后端答复-导入模板与图表编号口径》示例曾误写 `"code": 200`，正确应为 `"code": 0`——`200` 是 HTTP 状态码，不是业务码；成功码口径以本条为准。
- `meta`：**原样透传契约文件的 `meta` 字段**（`generated_at` / `script` / `dataset` / `n_samples` / `seed` / `schema_version`），前端据此渲染数据来源角标。
- **版本锚点（v2.0 新增）**：`meta` 增 `contract_ver`（API 契约版本，本次 `v2.0`）/ `enums_version`（实体枚举版本 `v1.0`）/ `schema_version`（库表版本 `v1.0`）；前端启动断言三者，不匹配显示「契约版本不一致，请刷新」而非静默错渲。
- 响应 JSON 字段名**直接沿用库表/契约字段名，不转 camelCase**（与 Q5 一致）。

- 构建期由 `scripts/build_enums.py` 派生 `configs/enums.json`（机器可读，前端直接 import）。
- 接口 payload 同时下发 `type`（英文，逻辑用）+ `type_cn`（中文，展示用），前端零本地映射。
- 前端删除 `renderGraph`/`showDetail` 硬编码，改消费 `enums.json`（`entityLabel`/`entityColor`，归前端 FE）。

### 3.3.3 局部解释 `feature_shap`（问题 3）

`explanations[id]` 增 `status`（`ready`/`pending`）与 `feature_shap`（对象式，非裸数组）：

```json
{
  "company_0": {
    "status": "ready",
    "baseline_pd": 0.7601,
    "neighbors": [ { "node_id": "investor_67", "type": "investor", "rel": "获投资", "delta": 0.0565 } ],
    "feature_shap": {
      "method": "tree_shap", "score_direction": "pd",
      "base_value": 0.107, "prediction": 0.183,
      "top_k": 5, "coverage": 0.72,
      "items": [ { "f": "x37", "name": null, "semantic_known": false, "label_ref": "字段字典待补",
                   "value": 0.0836, "raw_value": 1.42, "median": 0.81 } ]
    }
  }
}
```

- `name` 一律 `null`（不为 `semantic_known:false` 字段编业务名，红线二）。
- `score_direction: "pd"`（正值 = 推高 PD/风险），前端据此定红绿方向，避免国内「涨红跌绿」语境下反色。
- 未就绪时 `feature_shap: null`，前端占位「局部解释生成中」，**不用全局 `importance` 顶替**。
- `neighbors`（边归因 ΔPD）与 `feature_shap`（特征归因 SHAP）分区呈现，不做合并排序（量纲不同）。

### 3.3.4 版本锚点与精度（问题 5 / 6）

- `meta` 增 `contract_ver`/`enums_version`/`schema_version`（前端启动断言）。
- `score` 整数 0–100；`pd` 原始 float（展示格式由前端定，不把格式化数字当字符串下发）。
- 缺失一律 `null`，不用 `-1`/`0`/`""` 哨兵（与 §5.2「数据库层一律 NULL」一致）。
